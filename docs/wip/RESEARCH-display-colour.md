### Owner's machine (Fedora, Plasma 6.7.5, Wayland, RTX 5090 driver 615.71.9)
- `vulkaninfo`: the **native Wayland surface on the RTX 5090 offers `A2B10G10R10_UNORM_PACK32`** (and `A2R10G10B10`). The **X11/XWayland surfaces offer only `B8G8R8A8_UNORM/SRGB`.** So 10-bit works only if we run native Wayland (the default here).
- `kscreen-doctor -j` reports `iccProfilePath` per output (DP-4, DP-5, both calibrated ~sRGB-like profiles). `~/.config/kwinoutputconfig.json` stores the same per output (`connectorName`, `edidIdentifier`, `iccProfilePath`, `colorProfileSource: "ICC"`).
- `xprop -root _ICC_PROFILE`: not found. `colormgr get-devices`: empty. **So the X atom and colord are useless on KDE Wayland**; KDE keeps its profile in KScreen/KWin only.
- `wayland-info`: KWin advertises `wp_color_manager_v1` version 2 with features `parametric`, `extended_target_volume`, `set_mastering_display_primaries`, **but not `icc_v2_v4`**. So a client cannot read the output's ICC through the protocol, and cannot attach an ICC file to its own surface (only parametric descriptions).

## 1. How other apps do it

- **Linux/X11.** The "ICC Profiles in X" spec stores the profile in the root-window atom `_ICC_PROFILE` (`_ICC_PROFILE_n` for screen n). Per-output atoms were proposed but nobody read them. SOURCE: https://lists.freedesktop.org/archives/openicc/2011q2/004115.html , https://lists.freedesktop.org/archives/openicc/2010q3/002242.html . Chromium reads only the default-root atom: https://chromium.googlesource.com/chromium/src/+/013ac5eaf3/ui/gfx/icc_profile_x11.cc
- **colord.** Krita switched from the atom to colord for per-monitor profiles (Krita 2.9); GIMP offers "try to use the system monitor profile". SOURCE: https://lwn.net/Articles/460678/ , https://docs.gimp.org/3.0/en/gimp-prefs-color-management.html , https://docs.krita.org/de/reference_manual/preferences/color_management_settings.html . Krita lets the user set a profile per connected display and notes that under XWayland you should choose built-in sRGB.
- **darktable.** Preference "method to get the display profile": X atom or colord; its `darktable-cmstest` compares the two; on Wayland the two often disagree. SOURCE: https://discuss.pixls.us/t/darktable-cmstest-reports-different-profiles-for-x-atom-and-colord/44101 , https://discuss.pixls.us/t/yet-another-wayland-colour-managment-question/39673/12 (forum threads, not the manual).
- **KDE.** colord-kde may write the atom for the wrong monitor in multi-monitor setups: https://bugs.kde.org/show_bug.cgi?id=328248 . KWin (since Plasma 6) applies a per-screen ICC profile itself: https://planet.kde.org/xavers-blog-2023-12-17-an-update-on-hdr-and-color-management-in-kwin . Plasma 6.7 regressions with ICC profiles exist (e.g. https://bugs.kde.org/show_bug.cgi?id=522301), so test on 6.7.5.
- **Wayland protocol status.** `wp_color_management_v1`: KWin from Plasma 6.4 (v2 in 6.6), Mutter from GNOME 48, wlroots 0.19. SOURCE: https://www.phoronix.com/news/GNOME-wp_color_management_v1 , https://www.phoronix.com/news/wlroots-color-management , https://www.youngju.dev/blog/2026-07-17-wayland-color-management-hdr-shipping-timeline-xserver.en (secondary; dates not independently verified). Protocol: a client may read an output's ICC (`wp_color_management_output_v1.get_image_description` -> `get_information` -> `icc_file`) only if the compositor sends it; `icc_v2_v4` is optional: https://wayland.app/protocols/color-management-v1 . KWin 6.7.5 here does not offer it (see above). `kde_output_device_v2` is documented as not for regular clients: https://wayland.app/protocols/kde-output-device-v2
- **Windows.** `GetICMProfile` returns the profile path for a monitor DC, but is broken on Windows 11 (GIMP moved to `WcsGetDefaultColorProfile`; `ColorProfileGetDisplayDefault` for HDR/advanced colour). SOURCE: https://gitlab.gnome.org/GNOME/gimp/-/issues/7453 , https://learn.microsoft.com/en-us/windows/win32/api/icm/nf-icm-wcsgetdefaultcolorprofile , https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-geticmprofilea
- **macOS.** Chromium picks the `NSScreen` with the largest overlap with the window and reads `colorSpace.ICCProfileData`, and listens for `NSScreenColorSpaceDidChangeNotification`. SOURCE: https://chromium.googlesource.com/chromium/src/+/52.0.2743.116/ui/gfx/color_profile_mac.mm , https://developer.apple.com/documentation/appkit/nscolorspace.md . Our osascript reader does the same.
- **Dithering (mpv).** Default dither is `fruit` (a precomputed 64x64 matrix, `dither-size-fruit` = 6 by default); `ordered` is the older Bayer; libplacebo prefers blue noise where available. SOURCE: https://git.tjdev.de/mirror/mpv/commit/58a7d81dc55835fb0f5cc6a3f14288d722f83c91 , https://code.videolan.org/videolan/libplacebo/blob/aa04f95bf6590388921a065eccf9fda9219d091f/src/common.h . I could not fetch the current manual text; blue-noise/error-diffusion claims for mpv are UNVERIFIED. darktable and Blender detail not fetched (Blender: its OCIO view transform has an optional dither setting; UNVERIFIED).

## 2. CRITICAL RISK: double correction (must be understood before goal 1/2)

Compositors that colour-manage already convert "sRGB-tagged" surfaces to the monitor profile:
- **macOS**: wgpu 30 tags the CAMetalLayer with sRGB by default (`SurfaceColorSpace::Auto`), so macOS converts sRGB -> display profile. Our editor ALSO applies document -> monitor profile (profile read from NSScreen). Unless something untags the layer (I found no CAMetalLayer/colorspace code in apps/ or the UI crates) this is a **double correction** on macOS for any non-identity monitor profile (most visibly wide-gamut MacBook/Studio Display panels). Needs a quick test on the M4 Max: show a saturated sRGB patch with Monitor Profile = auto vs sRGB; it should look identical.
  - Right fix on macOS: set `SurfaceConfiguration.color_space = DisplayP3` (supported on all Metal formats) and make the display LUT target **Display P3** (not the NSScreen profile). macOS then does P3 -> panel. No `unsafe`, no osascript needed.
- **KWin Wayland with an ICC set (this machine)**: KWin converts untagged (sRGB) content to the panel profile. An app that also applies the profile double-corrects. KWin only accepts parametric surface tags, not ICC, so the correct app behaviour is "render in a standard space (sRGB or Display P3 via `wp_color_management_v1` parametric tagging) and let KWin do the rest". Wide-gamut documents then need the tag; plain sRGB output is safe today.
- **X11/XWayland, Windows (non-advanced colour)**: nothing converts, the app must do it (current design is right).

Design consequence: give "Monitor Profile = auto" a **mode** per platform/session: `AppManaged` (X11, Windows) vs `CompositorManaged` (macOS, KWin/Mutter/wlroots Wayland). In CompositorManaged mode, auto = "output space is sRGB/Display P3 as tagged"; the detected profile is shown in the UI for information but the transform is doc -> tagged space. An explicit user-picked profile always means AppManaged (current behaviour). Detect session by `XDG_SESSION_TYPE`/`WAYLAND_DISPLAY` and winit's backend.

## 3. Implementation plan (ordered)

### Step 1 (goal 3, smallest, no risk): dithered 8-bit output
- Add a dither + output-depth stage at the end of the canvas fragment shader `display_color()` (`gpu_canvas.rs:2623`): after the LUT/checker/grid, `rgb += (noise(frag_coord) - 0.5) / 255.0` (triangular-PDF is better: sum of two uncorrelated noises, +-1 LSB, no mean shift). Use a 64x64 blue-noise tile (tiny R8 texture generated at start with the void-and-cluster algorithm in Rust, or a baked 4 KB table; no new crate) or, at minimum, the interleaved-gradient noise egui already uses (https://blog.demofox.org/2022/01/01/interleaved-gradient-noise-a-different-kind-of-low-discrepancy-sequence/ , cited inside egui.wgsl). Add a uniform `depth_levels` (255 for 8-bit, 1023 for 10-bit, 0 = off) to the `view` uniform block.
- Dither only where the source is not already exact 8-bit: skip when the document is 8-bit and the display transform is the identity (no gain, avoids shimmer and `PartialEq` test breakage).
- CPU canvas (`CanvasDisplay::to_rgba8`) and Library/Develop CPU path: the float -> u8 quantise step should use a deterministic ordered/blue-noise dither (position-based, so repeat renders are identical). Do not dither exports.
- Keep `eframe dithering = true` (default) for the UI; it is harmless on 8-bit.
- Tests: pure-Rust unit test that a 0..1 horizontal ramp quantised through the dither function has mean error ~0 and no run of identical codes longer than the undithered ramp; kittest/golden for identity case unchanged; GPU test via `lc-ui-egui/src/gpu_test_support.rs`-style readback on `read_texels`.

### Step 2 (goal 1): Library/Develop use the monitor profile
- Today the preview is an 8-bit sRGB `ColorImage`. Minimum-change route: **CPU transform per preview** in the render job, reusing `photocraft_engine::display_color` (`CanvasDisplay`-like struct with source = sRGB (or Develop's working output space) and `apply_u8`, same cached `Transform`, `DisplayCaches::monitor_for(display)`), applied when building the texture (`lc-ui-egui/src/render.rs:535`). Cost: moxcms 8-bit LUT transform, a few ms per 2 MP preview; thumbnails (grid) are the volume problem, so transform thumbnails once at texture upload and key the thumbnail cache by monitor-profile hash (`CanvasDisplay::key`).
- Better, later: draw Develop's main image through a small paint callback using the same WGSL 3D-LUT sampling as `display_color()`; the lc-* crates would need access to the editor's LUT builder, so move `display_color.rs` + LUT builder into a shared crate (pc-engine -> `pc-cms` helper `build_display_lut(src, dst, size)`) that both pc-ui-egui and lc-ui-egui depend on. Check the layering rule first (lc-* and pc-* are separate trees; `lc-ui-egui` already depends on photocraft crates? verify before moving code).
- Identity short-circuit already exists (`is_identity`), so sRGB monitors cost nothing.
- Per-window profile: reuse `display_at(displays, window_rect)` and re-run on window move; Library/Develop share the main window so use the same `monitor_status`.
- Tests: unit test that sRGB -> a synthetic wide-gamut matrix profile changes a known patch by the expected amount (like `pc-vector/src/profile_tests.rs`); identity monitor leaves bytes unchanged; kittest golden with a fake monitor profile (`Edit > Color Settings` path override).

### Step 3 (goal 2): automatic profile detection on Linux (Windows later)
Pure-Rust detection chain, in order, behind one `monitor_profile::detect_async()` per platform (extends `apps/local-image/src/monitor_profile.rs`):
1. **KDE (this machine)**: read `~/.config/kwinoutputconfig.json` (`serde_json`, already used) -> entries with `iccProfilePath`, `connectorName`, `edidIdentifier`; match them to windows via winit `MonitorHandle::name()` (Wayland output name = connector, e.g. `DP-4`; winit 0.30 `MonitorHandle::name/position/size/scale_factor`). Fallback: run `kscreen-doctor -j` (std::process, 2 s timeout, like the macOS helper). This is the only source that works today on KWin (verified above).
2. **X11 / XWayland**: `x11rb` `get_property(root, _ICC_PROFILE[_n], CARD8)` (already a dependency; core protocol, no extra features); atom per screen. Use only when the window is an X11 window (`window.raw_window_handle()` is Xlib/Xcb).
3. **GNOME and others with colord**: `zbus` 5.19 (pure Rust, already in Cargo.lock; we would add it as a direct dependency, check tokio/async-io feature set to avoid duplicates) -> `org.freedesktop.ColorManager.GetDevicesByKind("display")` -> device `Profiles` -> `org.freedesktop.ColorManager.Profile.Filename`; match device by `Model`/`Serial`/`Metadata["OutputEdidMd5"]` or output name. Cheaper fallback with no new dependency: `colormgr get-devices-by-kind display` / `colormgr device-get-default-profile` text parse.
4. **Wayland protocol (future)**: `wayland-protocols 0.32.13` (in the lock) has `wp::color_management` (staging feature); read `icc_file` when a compositor offers `icc_v2_v4` (KWin 6.7.5 does not). Needs its own `wayland-client` connection (event queue) because winit owns eframe's; a second connection to the same display is allowed. Do not do this until a compositor sends ICC.
5. Else sRGB.
- Windows (later): `GetICMProfile` is unreliable on Windows 11; use `WcsGetDefaultColorProfile` via `winsafe`/`windows-sys` raw calls inside `lc-sysmem` (the only `unsafe` crate), per monitor via `MonitorFromWindow` + `GetMonitorInfo` device name; re-read on `WM_DISPLAYCHANGE`/`WM_DPICHANGED`. `windows-sys` is declaration-only Rust, but the repo's "no -sys crates" rule needs an owner decision; `winsafe` is already pinned.
- The mode rule from section 2 applies: on KWin/Mutter/wlroots Wayland and macOS the detected profile is shown but not applied in `auto`.
- Tests: pure parser tests with fixture JSON (copy the structure of `kwinoutputconfig.json`, redacted) and a fake `colormgr` output; X11 test behind `#[ignore]` (needs a server). Manual: move window between DP-4/DP-5 and watch the Colour Settings status line (`DisplayCaches::display_statuses`).

### Step 4 (goal 4): real 10-bit output with 8-bit dithered fallback
1. **Patch egui-wgpu** (no hook exists): vendor `egui-wgpu 0.36.2` into the repo (e.g. `vendor/egui-wgpu`) and add `[patch.crates-io] egui-wgpu = { path = "vendor/egui-wgpu" }`. The diff is ~15 lines: (a) a new field in `WgpuConfiguration`/`SurfaceConfig`, `preferred_formats: Vec<TextureFormat>` (or an `Arc<dyn Fn(&[TextureFormat]) -> TextureFormat>`), consulted at `lib.rs:278` instead of `preferred_framebuffer_format`; (b) optionally `color_space` copied into the `SurfaceConfiguration` built at `winit.rs:120`. Offer it upstream (emilk/egui) afterwards. Pure Rust, so the purity rule holds. Check Cargo.lock on every egui bump.
2. Choose `Rgb10a2Unorm` when it appears in `get_capabilities().formats` (NVIDIA native Wayland: yes; XWayland: no; Metal: if `format_rgb10a2_unorm_all`), keep `color_space = Auto` (sRGB) on Linux and `DisplayP3` on macOS. Prefer 10-bit over `Rgba16Float` (fp16 + `Auto` picks `ExtendedSrgbLinear`, which would need linear output and break egui's gamma pipeline).
3. UI is fine on 10-bit: egui picks `fs_main_gamma_framebuffer` for any non-sRGB format and writes gamma values; the UI just gets finer quantisation. Set `NativeOptions::dithering = false` when the surface is 10-bit (its noise is hard-coded for 256 levels: `dither_interleaved(.., 256.0, ..)`), and make the canvas shader use `depth_levels = 1023`.
4. **Display LUT precision**: the 3D LUT is RGBA8 (`gpu_canvas.rs:819`), which caps precision at 8-bit before interpolation. For 10-bit, build the LUT as `Rgba16Float` (filterable on all targets; 33^3 x 8 B = 290 KB) and compute it with float output from `Transform` (moxcms float path, `precise_float`). Also upload the 16-bit canvas texture (already `Rgba16Float`) un-quantised; 8-bit documents show only 8-bit levels anyway but the LUT output then gets real 10-bit values.
5. Compositor / driver notes: KWin chooses scanout depth itself (default 10 where the link allows; `KWIN_DRM_PREFER_COLOR_DEPTH=24` forces 8-bit) and the driver sets the real panel depth; a client cannot query the final depth. SOURCE: https://discuss.kde.org/t/kde-wayland-view-set-color-bit-depth/2019 . Displays at high refresh over DisplayPort may fall back to 8-bit: https://forums.developer.nvidia.com/t/cant-use-165hz-monitor-with-10bit-hdr-on-kde-plasma-6/305360 . Even with a 10-bit swapchain the panel may receive 8-bit + the driver's own dithering; nothing for us to do. On macOS the CAMetalLayer path handles it (`Rgb10a2Unorm`, `pixelFormat = .bgr10a2Unorm`; EDR is only for fp16 `wantsExtendedDynamicRangeContent`).
6. Fallback is automatic: no 10-bit format offered -> 8-bit format + step 1 dithering. Add a Preferences > Performance toggle "10-bit output (restart)" with `PHOTOCRAFT_SURFACE_10BIT=0` override, and log the chosen format in the GPU note (`gpu_startup`), so crashes in the crash-safe start chain (marker file) can drop to 8-bit like other fallbacks.
- Tests: unit-test the format chooser on synthetic format lists ([Bgra8Unorm,...] -> 8-bit; [Rgb10a2Unorm,Bgra8Unorm] -> 10-bit; sRGB-only list); GPU test (wgpu headless adapter) rendering a 0..1 ramp into an offscreen `Rgb10a2Unorm` target and counting distinct levels (>> 256) vs the same through the 8-bit path with dither (mean-error test); manual on this PC: native Wayland should log `Rgb10a2Unorm`; forced `WINIT_UNIX_BACKEND=x11` should log `Bgra8Unorm` (fallback test on a "non-10-bit" surface, which is available right here); `kscreen-doctor` can also limit max bpc on a connector for a hardware check.

## 5. Risks
- Double correction (section 2) - highest.
- Vendored egui-wgpu must be re-merged on every egui upgrade; mitigate with an upstream PR.
- Per-window profile switching and thumbnail-cache invalidation (cache key must include monitor profile hash).
- KWin 6.7 ICC regressions (bugs 522301, 524038) can look like our bug.
- Plasma without a profile set -> `colorProfileSource: "sRGB"`, `iccProfilePath: ""` -> treat as sRGB.
- NVIDIA exposes `A2R10G10B10` too; wgpu-hal maps only A2B10G10R10 (`conv.rs:176`), fine.

## 6. HDR (later, out of scope)
Needs: (1) swapchain `Rgba16Float` or `Rgb10a2Unorm` with `SurfaceColorSpace::ExtendedSrgbLinear/ExtendedSrgb` (macOS EDR: `wantsExtendedDynamicRangeContent`, headroom from wgpu `DisplayHdrInfo`, see `wgpu-hal metal/surface.rs:140-175`) or BT2100 PQ/HLG on Vulkan/Metal; (2) on Wayland the `wp_color_management_v1` surface tag (needs raw `wl_surface` access = a second Wayland connection and possibly `unsafe` in lc-sysmem; KWin 6.7.5 supports parametric with mastering primaries and `extended_target_volume`); (3) a tone-mapping/headroom stage in the final shader, a 32-bit float canvas path, an HDR-aware egui UI (UI composited at SDR white, scaled by the compositor's SDR brightness), and (4) Windows advanced-colour handling (`ColorProfileGetDisplayDefault`). Treat as a separate project after goals 1-4.
